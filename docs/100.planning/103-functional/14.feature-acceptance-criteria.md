# Feature Acceptance Criteria

## Overview
This document defines detailed acceptance criteria for each feature in the Unique ID Generator service.

---

## Feature F-01: Generate Unique ID

### Description
Generate unique 64-bit IDs via HTTP GET endpoint

### Acceptance Criteria

| ID | Criteria | Test Scenario | Priority |
|----|----------|---------------|----------|
| AC-F01-01 | GET /generate returns a 64-bit integer | Call endpoint, verify response contains `id` field as integer | P0 |
| AC-F01-02 | Generated ID is within 64-bit unsigned range (0 to 2^64-1) | Generate 1000 IDs, verify all >= 0 and < 18446744073709551616 | P0 |
| AC-F01-03 | Generated ID has correct Snowflake structure | Parse 100 IDs, verify timestamp/datacenter/machine/sequence bits | P0 |
| AC-F01-04 | No two IDs generated within 1ms on same machine are identical | Burst test: 4096 IDs in 1ms, verify uniqueness | P0 |
| AC-F01-05 | IDs across different machines are unique | Generate 1M IDs from 3 instances, verify no collisions | P0 |
| AC-F01-06 | Response time P99 < 50ms | Load test at 10K RPS, measure P99 latency | P0 |

### Edge Cases

| Case | Handling |
|------|----------|
| Sequence overflow (>4095 in 1ms) | Wait until next millisecond |
| Clock goes backwards | Return 500 CLOCK_BACKWARDS |
| All generators down | Return 503 GENERATORS_UNAVAILABLE |

## Feature F-02: JSON Response

### Description
Return IDs as numerical values in JSON format

### Acceptance Criteria

| ID | Criteria | Test Scenario | Priority |
|----|----------|---------------|----------|
| AC-F02-01 | Response Content-Type is application/json | Check response headers | P0 |
| AC-F02-02 | Response body contains `id` key | Parse JSON, verify key exists | P0 |
| AC-F02-03 | ID value is a JSON number (not string) | Verify `typeof id === 'number'` | P0 |
| AC-F02-04 | Response is valid JSON | JSON.parse() succeeds | P0 |

### Example Response

```json
{
  "id": 1825478541164436481
}
```

## Feature F-03: Concurrent Requests

### Description
Support concurrent requests without collisions

### Acceptance Criteria

| ID | Criteria | Test Scenario | Priority |
|----|----------|---------------|----------|
| AC-F03-01 | 1000 concurrent requests to 1 generator | All IDs unique | P0 |
| AC-F03-02 | 1000 concurrent requests to 3 generators | All IDs unique | P0 |
| AC-F03-03 | Lock prevents race conditions | Verify no duplicate sequences | P0 |
| AC-F03-04 | No blocking under high concurrency | P99 latency < 50ms at 10K RPS | P0 |

### Thread Safety Requirements

- [ ] asyncio.Lock protects shared state (sequence, last_timestamp)
- [ ] Lock acquisition time < 1ms P99
- [ ] No deadlock possible under any scenario

## Feature F-04: Time Ordering

### Description
Time-based ordering within a single generator

### Acceptance Criteria

| ID | Criteria | Test Scenario | Priority |
|----|----------|---------------|----------|
| AC-F04-01 | IDs generated on same machine are monotonically increasing | Generate 1000 IDs, verify each > previous | P0 |
| AC-F04-02 | IDs across milliseconds have correct order | Generate with 1ms delay, verify order | P0 |
| AC-F04-03 | Sequence resets to 0 at millisecond boundary | Verify sequence=0 after timestamp change | P0 |
| AC-F04-04 | ID parsing extracts correct timestamp | Parse ID, verify timestamp extraction | P1 |

### Guarantees

| Scope | Guarantee |
|-------|-----------|
| Within single generator | Monotonically increasing |
| Within single millisecond | Unique via sequence |
| Across generators | Not guaranteed |

## Feature F-05: PostgreSQL Persistence

### Description
Persist generated IDs to PostgreSQL (optional/auditing)

### Acceptance Criteria

| ID | Criteria | Test Scenario | Priority |
|----|----------|---------------|----------|
| AC-F05-01 | IDs are persisted to database | Generate 100 IDs, query DB, verify 100 records | P1 |
| AC-F05-02 | Writes are async (non-blocking) | Verify P99 latency unchanged with persistence | P1 |
| AC-F05-03 | Database failure doesn't block ID generation | Kill DB, generate IDs, verify success | P1 |
| AC-F05-04 | Graceful recovery when DB returns | Restart DB, verify writes resume | P1 |
| AC-F05-05 | Duplicate IDs handled idempotently | Attempt duplicate insert, no error | P2 |

### Database Schema

```sql
CREATE TABLE generated_ids (
    id BIGINT PRIMARY KEY,
    timestamp_ms BIGINT NOT NULL,
    datacenter_id SMALLINT NOT NULL,
    machine_id SMALLINT NOT NULL,
    sequence_num SMALLINT NOT NULL,
    generated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    metadata JSONB
);
```

## Feature F-06: Health Dashboard

### Description
Web dashboard to monitor generator health

### Acceptance Criteria

| ID | Criteria | Test Scenario | Priority |
|----|----------|---------------|----------|
| AC-F06-01 | Dashboard displays all 3 instances | Open dashboard, verify 3 rows | P1 |
| AC-F06-02 | Instance status updates every 5 seconds | Check network tab, verify polling | P1 |
| AC-F06-03 | OK status shown with green indicator | Healthy instance shows green | P1 |
| AC-F06-04 | DEGRADED status shown with yellow indicator | Degraded instance shows yellow | P1 |
| AC-F06-05 | DOWN status shown with red indicator | Down instance shows red | P1 |
| AC-F06-06 | Uptime displayed in human-readable format | Verify "2d 14h 32m" format | P2 |
| AC-F06-07 | IDs generated counter displayed | Verify number matches /health response | P2 |

### Dashboard UI Requirements

- [ ] Responsive layout (mobile-friendly)
- [ ] Loading states during data fetch
- [ ] Error states when API unavailable
- [ ] Auto-refresh every 5 seconds

## Error Handling Acceptance Criteria

| Error Code | HTTP Status | Trigger | Expected Response |
|------------|-------------|---------|-------------------|
| CLOCK_BACKWARDS | 500 | Clock goes backwards | `{"error": "...", "code": "CLOCK_BACKWARDS"}` |

## BDD Scenarios

### Scenario: Generate Unique ID - Happy Path

```
Given a healthy generator instance
When I call GET /generate
Then I receive a JSON response with {"id": <64-bit-integer>}
And the id is globally unique
```

### Scenario: Generate Unique ID - Sequence Overflow

```
Given a generator has generated 4096 IDs in the same millisecond
When I call GET /generate again
Then the generator waits for the next millisecond
And returns a unique ID with sequence=0
```

### Scenario: Generate Unique ID - Clock Backwards

```
Given the system clock went backwards
When I call GET /generate
Then I receive HTTP 500
And the response contains {"code": "CLOCK_BACKWARDS"}
```

### Scenario: Health Check - All Healthy

```
Given all 3 generator instances are healthy
When I call GET /health on each instance
Then each returns {"status": "ok", ...}
```

### Scenario: Health Check - One Down

```
Given generator-2 is down
When I call GET /health on nginx
Then requests route to generator-1 or generator-3
And I receive valid IDs
```
