# Concurrency Design

## Overview
This document specifies the concurrency design for handling 10,000+ RPS while ensuring zero ID collisions across all generator instances.

## Concurrency Requirements

| Requirement | Value |
|-------------|-------|
| Target RPS | 10,000 |
| Peak RPS | 15,000 |
| Per-generator capacity | 4,096,000 IDs/second |
| Max concurrent connections | 100-1000 per generator |
| Collision tolerance | Zero |

## Single-Generator Concurrency

### Thread Safety Design

Each generator instance uses an asyncio Lock to ensure thread-safe ID generation:

```python
import asyncio
from dataclasses import dataclass

EPOCH = 1288834974657

@dataclass
class IdGenerator:
    datacenter_id: int
    machine_id: int
    sequence: int = 0
    last_timestamp_ms: int = 0
    _lock: asyncio.Lock = None

    def __post_init__(self):
        self._lock = asyncio.Lock()

    def _build_id(self, timestamp_ms: int, sequence: int) -> int:
        """Build 64-bit Snowflake ID from components."""
        return (
            (timestamp_ms << 22) |
            (self.datacenter_id << 17) |
            (self.machine_id << 12) |
            sequence
        )

    async def generate_id(self) -> int:
        """Generate a unique 64-bit ID."""
        async with self._lock:
            current_ms = int(time.time() * 1000)

            # Handle same millisecond
            if current_ms == self.last_timestamp_ms:
                self.sequence += 1
                if self.sequence >= 4096:
                    # Wait for next millisecond
                    while current_ms == self.last_timestamp_ms:
                        current_ms = int(time.time() * 1000)
                        await asyncio.sleep(0.001)
                    self.sequence = 0
            else:
                self.sequence = 0

            # Check for clock backwards
            if current_ms < self.last_timestamp_ms:
                raise ClockBackwardsError(
                    f"Clock backwards: {current_ms} < {self.last_timestamp_ms}"
                )

            self.last_timestamp_ms = current_ms

            return self._build_id(current_ms, self.sequence)
```

### Lock Granularity

| Design | Pros | Cons | Decision |
|--------|------|------|----------|
| Coarse lock (entire method) | Simple, safe | Lower throughput | ✓ Chosen |
| Fine-grained (per component) | Higher throughput | Complex, risk of bugs | Not chosen |

## Multi-Generator Collision Prevention

### Unique (Datacenter, Machine) Tuple

Each generator instance MUST have a unique combination of datacenter_id and machine_id:

| Instance | Datacenter ID | Machine ID | Tuple |
|----------|---------------|------------|-------|
| Generator 1 | 1 | 1 | (1, 1) |
| Generator 2 | 1 | 2 | (1, 2) |
| Generator 3 | 1 | 3 | (1, 3) |

### Collision Proof

The Snowflake algorithm guarantees uniqueness because:

```
ID = (timestamp << 22) | (datacenter_id << 17) | (machine_id << 12) | sequence
```

Given unique (datacenter_id, machine_id) tuples:
- No two generators can produce the same ID even in the same millisecond
- Sequence uniqueness within a generator is maintained by the lock

**Mathematical Proof:**
- Per-generator per-ms uniqueness: sequence 0-4095 (12 bits)
- Cross-generator uniqueness: (datacenter_id, machine_id) tuple + different timestamps
- At 10,000 RPS with 3 generators, each generator handles ~3,333 RPS
- Each generator can handle 4,096,000 IDs/second (4ms burst capacity)

## Async vs Sync Design

### Python Async Approach

Using asyncio for concurrent request handling:

```python
import asyncio
from aiohttp import web

async def generate_handler(request):
    try:
        id = await request.app['generator'].generate_id()
        return web.json_response({'id': id})
    except ClockBackwardsError as e:
        return web.json_response(
            {'error': str(e), 'code': 'CLOCK_BACKWARDS'},
            status=500
        )

async def init_app():
    app = web.Application()
    app['generator'] = IdGenerator(datacenter_id=1, machine_id=1)
    app.router.add_get('/generate', generate_handler)
    return app
```

### Why asyncio over threading?

| Aspect | asyncio | threading |
|--------|---------|----------|
| GIL | No issue | Blocks concurrency |
| Memory | Lower | Higher (stack per thread) |
| Complexity | Medium | High (locks everywhere) |
| Throughput (this use case) | High | Sufficient |
| Decision | ✓ Chosen | ✗ Not chosen |

## Request Flow: Single Generator

```
Request 1 ──┐
Request 2 ──┼──▶ Lock ──▶ Generate ──▶ Release ──▶ Response
Request 3 ──┤                ▲
            │                │
            └────── Wait ────┘
```

### Timing Analysis

| Operation | Time |
|-----------|------|
| Lock acquire | ~0.001ms |
| Timestamp get | ~0.001ms |
| Sequence increment | ~0.001ms |
| ID building | ~0.001ms |
| Lock release | ~0.001ms |
| **Total** | ~0.005ms |

**Conclusion:** Lock overhead is negligible compared to 50ms budget.
