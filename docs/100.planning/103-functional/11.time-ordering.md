# Time Ordering Specification

## Overview
This document specifies how time ordering works within the Snowflake ID system, including guarantees and limitations.

## Time Ordering Guarantees

| Scope | Guarantee | Mechanism |
|-------|-----------|-----------|
| Within single generator | Monotonically increasing | Sequence number per ms |
| Across generators | Not guaranteed | Clock drift possible |
| Within single millisecond | Unique via sequence | 12-bit counter |

## Timestamp Component

### Epoch

**Twitter Snowflake Epoch:** 1288834974657 (Nov 04, 2010, 01:42:54.657 UTC)

This epoch was chosen by Twitter to allow for ~69 years of IDs while keeping the timestamp positive in a signed 64-bit context.

### Timestamp Bit Layout

```
Bits 62-22 (41 bits): Milliseconds since epoch
```

### Time Range Calculation

```
2^41 - 1 = 2,199,023,255,551 ms
2,199,023,255,551 / (1000 * 60 * 60 * 24 * 365.25) ≈ 69.7 years

Start: Nov 04, 2010
End: ~2080 (2010 + 69.7 years)
```

## ID Parsing Functions

### Python Implementation

```python
EPOCH = 1288834974657

def parse_id(id: int) -> dict:
    """Parse a Snowflake ID into its components."""
    return {
        'id': id,
        'timestamp_ms': (id >> 22),
        'datacenter_id': (id >> 17) & 0x1F,
        'machine_id': (id >> 12) & 0x1F,
        'sequence': id & 0xFFF,
    }

def parse_timestamp(id: int) -> datetime:
    """Extract timestamp as datetime from Snowflake ID."""
    timestamp_ms = (id >> 22) + EPOCH
    return datetime.fromtimestamp(timestamp_ms / 1000, tz=timezone.utc)

def parse_sequence(id: int) -> int:
    """Extract sequence number from Snowflake ID."""
    return id & 0xFFF

def parse_machine_id(id: int) -> int:
    """Extract machine ID from Snowflake ID."""
    return (id >> 12) & 0x1F

def parse_datacenter_id(id: int) -> int:
    """Extract datacenter ID from Snowflake ID."""
    return (id >> 17) & 0x1F

def get_datetime_components(id: int) -> dict:
    """Get full datetime breakdown from ID."""
    timestamp_ms = (id >> 22) + EPOCH
    dt = datetime.fromtimestamp(timestamp_ms / 1000, tz=timezone.utc)
    return {
        'datetime': dt,
        'year': dt.year,
        'month': dt.month,
        'day': dt.day,
        'hour': dt.hour,
        'minute': dt.minute,
        'second': dt.second,
        'millisecond': dt.microsecond // 1000,
        'timestamp_ms': timestamp_ms,
    }
```

## ID Reconstruction

### Build ID from Components

```python
def build_id(timestamp_ms: int, datacenter_id: int,
             machine_id: int, sequence: int) -> int:
    """Build a Snowflake ID from components."""
    return (
        (timestamp_ms << 22) |
        (datacenter_id << 17) |
        (machine_id << 12) |
        sequence
    )

def verify_id(id: int) -> bool:
    """Verify an ID has correct structure."""
    components = parse_id(id)
    return (
        components['datacenter_id'] <= 31 and
        components['machine_id'] <= 31 and
        components['sequence'] <= 4095
    )
```

## Sortability Analysis

### Within a Single Generator

IDs generated by a single generator are **guaranteed** to be monotonically increasing because:

1. Within the same millisecond: sequence increments (0 → 1 → 2 → ...)
2. Across milliseconds: timestamp increments

**Example:**
```
ID1: timestamp=1000, sequence=0  → 1000 << 22 + 0
ID2: timestamp=1000, sequence=1  → 1000 << 22 + 1  (ID2 > ID1)
ID3: timestamp=1001, sequence=0  → 1001 << 22 + 0  (ID3 > ID2)
```

### Across Multiple Generators

IDs generated by **different generators** may NOT be in true time order due to:

1. **Clock drift:** Generators may have slightly different system clocks
2. **Network latency:** Requests arrive at different times

**Example of out-of-order across generators:**
```
Generator 1 (clock slightly fast):  ID_A timestamp=1010
Generator 2 (clock slightly slow):  ID_B timestamp=1009
ID_A > ID_B numerically (correct time order would be ID_B < ID_A)
```

**However:** Within each generator's IDs, the order is always correct.

## Global Ordering Workaround

If global ordering is required, client applications can:

1. **Sort by (timestamp_ms, datacenter_id, machine_id, sequence)**
2. **Use the ID itself with tiebreaker:** `(id >> 12)` gives a rough time order

### Sorting Algorithm

```python
def sort_ids_globally(ids: list[int]) -> list[int]:
    """Sort IDs with rough global time ordering."""
    return sorted(ids, key=lambda id: (id >> 12))

def sort_ids_exact(ids: list[int]) -> list[int]:
    """Sort IDs with exact ordering (requires timestamp extraction)."""
    return sorted(ids, key=lambda id: parse_id(id)['timestamp_ms'])
```

## Clock Synchronization

### NTP Requirements

| Requirement | Value |
|-------------|-------|
| Max clock drift | ±10ms between generators |
| Drift check interval | 1 second |
| NTP query interval | 60 seconds |
| Acceptable NTP sources | 3+ |

### Drift Detection

```python
class ClockValidator:
    def __init__(self):
        self._last_time_ms = 0
        self._drift_count = 0
        self._max_drift_ms = 0

    def validate(self, current_ms: int) -> Tuple[bool, str, int]:
        """Validate timestamp is monotonic."""
        if current_ms < self._last_time_ms:
            drift = self._last_time_ms - current_ms
            self._drift_count += 1
            self._max_drift_ms = max(self._max_drift_ms, drift)

            if drift > 10:
                return False, "CRITICAL", drift
            elif drift > 1:
                return False, "WARNING", drift
            else:
                return False, "INFO", drift

        self._last_time_ms = current_ms
        return True, "OK", 0
```

### Drift Thresholds

| Drift | Severity | Action |
|-------|----------|--------|
| < 1ms | OK | Accept |
| 1-10ms | WARNING | Log warning, continue |
| > 10ms | CRITICAL | Stop generation, alert ops |

## Sortability Tests

### Test T1: Single Generator Ordering

```python
def test_single_generator_ordering():
    generator = IdGenerator(datacenter_id=1, machine_id=1)
    ids = [generator.generate_id() for _ in range(1000)]

    # IDs should be monotonically increasing
    for i in range(1, len(ids)):
        assert ids[i] > ids[i-1], f"IDs not monotonically increasing at {i}"
```

### Test T2: Multi-Millisecond Ordering

```python
def test_multi_millisecond_ordering():
    generator = IdGenerator(datacenter_id=1, machine_id=1)

    # Generate batch with 1ms delay
    batch1 = [generator.generate_id() for _ in range(100)]
    time.sleep(0.001)  # 1ms delay
    batch2 = [generator.generate_id() for _ in range(100)]

    # All batch2 IDs > all batch1 IDs
    assert min(batch2) > max(batch1), "Batches not ordered"
```

### Test T3: ID Parsing Consistency

```python
def test_parsing_consistency():
    original_id = 1825478541164436481
    components = parse_id(original_id)
    reconstructed_id = build_id(**components)

    assert original_id == reconstructed_id, "ID reconstruction failed"
```

## Performance Considerations

### Timestamp Extraction Speed

| Operation | Time |
|----------|------|
| Bit shift (>> 22) | ~0.001ms |
| Add epoch | ~0.001ms |
| datetime conversion | ~0.1ms |

**Recommendation:** For high-throughput sorting, use `(id >> 12)` as a sort key rather than full timestamp extraction.
