## Step 3 — Run Event Storming

### 3.1 — Map Core Workflow as Domain Events

**Owner:** Tech Lead + Product Owner
**Sprint:** Planning Sprint 1
**Timebox:** 4 hours (workshop)

**Workflow Steps:**

```
1. ClientService --[requests ID]--> LoadBalancer
2. LoadBalancer --[routes request]--> GeneratorInstance
3. GeneratorInstance --[generates ID using Snowflake algorithm]--> IdGenerated
4. IdGenerated --[returned to client]--> ClientService
5. (Optional) IdGenerated --[persisted to]--> PostgreSQL
6. (Optional) IdGenerated --[logged]--> AuditLog
```

**Domain Events:**

| Event | Trigger | Payload | Consumers |
|-------|---------|---------|-----------|
| IdGenerated | Successful ID generation | {id, timestamp, datacenterId, machineId, sequence} | Client, (PostgreSQL) |
| IdPersistRequested | ID persistence enabled | {id, metadata, requestedAt} | PostgreSQL |
| GeneratorInstanceStarted | Instance bootstrap | {instanceId, datacenterId, machineId, startedAt} | Monitoring |
| GeneratorInstanceStopped | Graceful shutdown | {instanceId, reason, stoppedAt} | Monitoring |
| GeneratorInstanceFailed | Unrecoverable error | {instanceId, error, failedAt} | Alerting |

### 3.2 — Identify Anti-Events (Error Conditions)

**Anti-Events (Error Scenarios):**

| Anti-Event | Trigger | Handling |
|------------|---------|----------|
| IdGenerationFailed | Clock went backwards or sequence overflow | Return 500, alert ops |
| AllGeneratorsUnavailable | All 3 instances down | Return 503, alert ops |
| DatabaseUnavailable | PostgreSQL unreachable | Continue without persistence, alert ops |
| SequenceOverflow | More than 4096 requests in 1ms | Wait for next millisecond |

**Output:** `docs/100.planning/03.event-storming.md`

## Step 4 — Define Bounded Contexts

### 4.1 — Context Discovery

**Owner:** Tech Lead
**Sprint:** Planning Sprint 1
**Timebox:** 3 hours

**Candidate Contexts:**

| Context | Responsibility | Entities | Boundaries |
|---------|---------------|----------|------------|
| **ID Generation** | Generate unique, time-ordered IDs using Snowflake algorithm | Generator, Id | Core domain; no external dependencies |
| **Persistence** | Store generated IDs for auditing | GeneratedId, AuditLog | Reads from ID Generation; writes to PostgreSQL |
| **Load Balancing** | Route requests to available generators | Upstream, Downstream | Reads generator health; writes routing rules |
| **Monitoring** | Expose health metrics and dashboard | HealthStatus, Metrics | Reads from all contexts; no writes |

## Step 5 — Define Business Rules (Invariants)

### 5.1 — Invariants per Context

**ID Generation Context:**

| Rule | Statement | Enforcement |
|------|-----------|-------------|
| I-001 | An ID must never collide with any other ID | Algorithm guarantees |
| I-002 | IDs generated on the same machine must be monotonically increasing | Sequence counter |
| I-003 | Sequence number must reset to 0 every millisecond | Clock abstraction |
| I-004 | Timestamp must never go backwards | Clock monotonicity check |
| I-005 | Maximum 4096 IDs per millisecond per machine | Sequence overflow handling |

### 5.2 — Anti-Pattern Check

| Anti-Pattern | Status | Mitigation |
|--------------|--------|------------|
| Anemic Domain | Rejected | Business logic lives in Generator service |
| Gold-Plating | Rejected | No multi-region, no sharding in v1 |
| Resume-Driven Dev | Rejected | Python chosen (team skill), not latest trend |

**Output:** `docs/100.planning/05.invariants.md`
