## Step 1 — Validate 64-bit ID Structure

### 1.1 — Document ID Structure

**Owner:** Tech Lead
**Sprint:** Planning Sprint 1
**Timebox:** 2 hours

**ID Structure (64 bits):**

```
┌────────────┬────────────────────┬───────────────┬─────────────┬──────────────┐
│  Sign Bit  │    Timestamp       │  Datacenter   │   Machine   │   Sequence   │
│    (1)     │      (41)          │     (5)       │    (5)      │    (12)      │
├────────────┼────────────────────┼───────────────┼─────────────┼──────────────┤
│     0      │  ms since epoch    │   0-31        │   0-31      │   0-4095     │
└────────────┴────────────────────┴───────────────┴─────────────┴──────────────┘
```

**Field Specifications:**

| Field | Bits | Range | Epoch | Description |
|-------|------|-------|-------|-------------|
| Sign | 1 | 0 | - | Reserved; always 0 |
| Timestamp | 41 | 0-69 years | 1288834974657 (Nov 04, 2010) | Milliseconds since epoch |
| Datacenter ID | 5 | 0-31 (32 datacenters) | - | Identifies datacenter |
| Machine ID | 5 | 0-31 (32 machines/DC) | - | Identifies machine within datacenter |
| Sequence | 12 | 0-4095 (per ms/machine) | - | Auto-increment per millisecond |

**Maximum Capacity Calculation:**

| Metric | Calculation | Value |
|--------|------------|-------|
| Max IDs per ms per machine | 2^12 | 4,096 |
| Max IDs per second per machine | 4,096 × 1,000 | 4,096,000 |
| Max IDs per second per datacenter | 4,096,000 × 32 | 131,072,000 |
| Total max IDs across all datacenters | 131,072,000 × 32 | 4,194,304,000 |
| Timestamp range (years) | 2^41 / (1000 × 60 × 60 × 24 × 365.25) | ~69 years |
| Effective start date | Epoch + now | Nov 04, 2010 + 16 years = ~2026 |

**Validation Checklist:**
- [ ] Sign bit is always 0
- [ ] Timestamp uses Twitter Snowflake epoch (1288834974657)
- [ ] Datacenter ID is 5 bits (0-31)
- [ ] Machine ID is 5 bits (0-31)
- [ ] Sequence is 12 bits (0-4095), resets every ms
- [ ] ID fits in unsigned 64-bit integer
- [ ] ID is sortable by timestamp component

**Output:** `docs/100.planning/06.id-structure.md`

## Step 2 — Quantify Non-Functional Requirements

### 2.1 — Throughput Analysis

**Owner:** Tech Lead + DevOps
**Sprint:** Planning Sprint 1
**Timebox:** 3 hours

**Business Requirement:**
> Ability to generate over 10,000 unique IDs per second

**Technical Validation:**

| Scenario | Requirement | Design Headroom | Target |
|----------|-------------|-----------------|--------|
| Normal load | 10,000 RPS | 2× | 20,000 RPS |
| Peak load | 10,000 RPS | 3× | 30,000 RPS |
| Single generator (1 of 3) | 10,000 RPS | 2× | 20,000 RPS |

**Per-Generator Capacity:**
```
4,096 IDs/ms × 1,000 ms/s = 4,096,000 IDs/s per generator
```

**Validation:**
- [ ] Single generator: 4,096,000 >> 10,000 ✓
- [ ] 3 generators: 12,288,000 >> 10,000 ✓
- [ ] 10,000 RPS is well within single-generator capacity

**Conclusion:** Single generator can handle 10,000 RPS easily. 3 instances provide redundancy, not capacity.

### 2.2 — Latency Analysis

**Owner:** Tech Lead
**Sprint:** Planning Sprint 1
**Timebox:** 2 hours

**Business Requirement:**
> P99 < 50ms per ID generation request

**Latency Budget Breakdown:**

| Component | P50 | P95 | P99 | Notes |
|-----------|-----|-----|-----|-------|
| nginx routing | 0.1ms | 0.2ms | 0.5ms | In-memory LB |
| Python service | 0.01ms | 0.02ms | 0.05ms | Pure computation |
| Network (local) | 0.5ms | 1ms | 2ms | localhost |
| PostgreSQL (optional) | 1ms | 5ms | 10ms | Async write |
| **Total** | **~2ms** | **~7ms** | **~13ms** | With headroom |

**Validation:**
- [ ] P99 50ms requirement is achievable
- [ ] Design headroom: 50ms - 13ms = 37ms buffer
- [ ] No database synchronous writes in hot path

### 2.3 — Availability Analysis

**Owner:** Tech Lead + DevOps
**Sprint:** Planning Sprint 1
**Timebox:** 2 hours

**Business Requirement:**
> 99.9% uptime (3 nines)

**Availability Calculation:**

| Period | 99.9% Allowed Downtime |
|--------|------------------------|
| Per day | 1.44 minutes |
| Per week | 10.08 minutes |
| Per month | 43.83 minutes |
| Per year | 8.76 hours |

**Redundancy Design:**

| Component | Instances | Failure Mode |
|-----------|-----------|--------------|
| nginx | 1 | Single point of failure (acceptable for internal) |
| Generator | 3 | 1 can fail; 2 remain (67% capacity) |
| PostgreSQL | 1 | No HA; data loss risk on failure |

**Validation:**
- [ ] 3 generator instances: 1 failure = 67% capacity (acceptable)
- [ ] nginx single instance: internal service only
- [ ] PostgreSQL single instance: data loss risk if it fails

### 2.4 — Consistency Analysis

**Owner:** Tech Lead
**Sprint:** Planning Sprint 1
**Timebox:** 2 hours

**CAP Trade-off Decision:**

| Option | Description | Chosen |
|--------|-------------|--------|
| CP (Consistency) | IDs never collide; service unavailable if split | ✓ |
| AP (Availability) | IDs may have rare collisions; always available | ✗ |

**Rationale:**
- ID collision is **unacceptable** — creates data integrity issues downstream
- Service unavailability during partition is **acceptable** — clients retry
- Zero tolerance for silent data corruption

**Validation:**
- [ ] CP chosen explicitly
- [ ] No eventual-consistency mechanisms needed
- [ ] Clock synchronization critical (NTP required)

### 3.2 — Create Architecture Decision Records (ADRs)

**ADR-001: nginx as Load Balancer**

| Field | Content |
|-------|---------|
| Context | Need a load balancer to distribute requests across 3 generator instances |
| Options | nginx, HAProxy, AWS ALB, Traefik |
| Decision | nginx |
| Rationale | Simple, battle-tested, well-understood by team, low resource footprint |
| Consequences | Single point of failure; no built-in health check auto-recovery |

**ADR-002: Python as Generator Language**

| Field | Content |
|-------|---------|
| Context | Need a generator service that produces IDs at 10,000+ RPS |
| Options | Python, Go, Rust, Node.js, Java |
| Decision | Python |
| Rationale | Team expertise, simplicity, fast development iteration |
| Consequences | GIL concern for threading (mitigated: single-threaded async); 10K RPS easily achievable |

**ADR-003: PostgreSQL for Persistence**

| Field | Content |
|-------|---------|
| Context | Need to persist generated IDs for auditing |
| Options | PostgreSQL, MySQL, MongoDB, Redis |
| Decision | PostgreSQL |
| Rationale | Team expertise, ACID compliance, JSON support, reliable |
| Consequences | Single instance (no HA); optional persistence (can be disabled) |

**ADR-004: Vite for Web Dashboard**

| Field | Content |
|-------|---------|
| Context | Need a web dashboard to monitor generator health |
| Options | Vite + React, Next.js, Vue, Svelte |
| Decision | Vite + React |
| Rationale | Fast dev server, modern tooling, team expertise |
| Consequences | SPA; needs backend API for health data |

**ADR-005: Docker for Containerization**

| Field | Content |
|-------|---------|
| Context | Need to containerize all services for deployment |
| Options | Docker, Podman, Kubernetes, bare-metal |
| Decision | Docker |
| Rationale | Standard containerization, docker-compose for local dev |
| Consequences | Single-node deployment initially; no auto-scaling without K8s |

**Output:** `docs/100.planning/adr/001-nginx-load-balancer.md`, `002-python-generator.md`, `003-postgresql-persistence.md`, `004-vite-dashboard.md`, `005-docker-containerization.md`

## Step 5 — Create API Contracts (OpenAPI)

### 5.1 — ID Generation API

**Owner:** Tech Lead
**Sprint:** Planning Sprint 1
**Timebox:** 3 hours

**OpenAPI Specification:**

```yaml
openapi: 3.0.3
info:
  title: Unique ID Generator API
  version: 1.0.0
  description: Distributed unique ID generation service

paths:
  /generate:
    get:
      summary: Generate a unique ID
      operationId: generateId
      tags:
        - ID Generation
      responses:
        '200':
          description: Successfully generated ID
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/GenerateResponse'
        '503':
          description: No generators available
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/ErrorResponse'

  /health:
    get:
      summary: Health check
      operationId: healthCheck
      tags:
        - Monitoring
      responses:
        '200':
          description: Service is healthy
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/HealthResponse'

components:
  schemas:
    GenerateResponse:
      type: object
      required:
        - id
      properties:
        id:
          type: integer
          format: int64
          description: 64-bit unique identifier
          example: 1825478541164436481

    HealthResponse:
      type: object
      required:
        - status
        - instance
      properties:
        status:
          type: string
          enum: [ok, degraded, down]
        instance:
          type: string
          description: Datacenter-machine identifier
          example: "dc-01-machine-03"

    ErrorResponse:
      type: object
      required:
        - error
        - code
      properties:
        error:
          type: string
          description: Human-readable error message
        code:
          type: string
          description: Machine-readable error code
          example: "GENERATORS_UNAVAILABLE"
```

## Step 7 — Define State Machines

### 7.1 — Generator Instance Lifecycle

**Owner:** Tech Lead
**Sprint:** Planning Sprint 1
**Timebox:** 2 hours

**State Diagram:**

```
                    ┌─────────────────────────────────────────┐
                    │                                         │
                    ▼                                         │
┌──────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────┴─────┐
│ STARTING │───▶│   HEALTHY    │───▶│  DEGRADED    │───▶│   STOPPED  │
└──────────┘    └──────────────┘    └──────────────┘    └────────────┘
     │                 │                  │
     │                 │                  │
     │                 ▼                  ▼
     │          ┌──────────────┐    ┌──────────────┐
     └─────────▶│    FAILED    │───▶│   STOPPED     │
                └──────────────┘    └───────────────┘
```

**States:**

| State | Description | Entry Criteria | Exit Criteria |
|-------|-------------|----------------|---------------|
| STARTING | Initializing | Process start | Health check passes |
| HEALTHY | Normal operation | Startup complete | Sequence overflow or clock error |
| DEGRADED | Limited capacity | Clock sync issue | Normal operation resumed |
| FAILED | Unrecoverable error | Fatal exception | Manual restart required |
| STOPPED | Process terminated | Graceful shutdown | - |

**Transitions:**

| From | To | Trigger | Action |
|------|----|---------|--------|
| - | STARTING | Process spawn | Initialize clock, load config |
| STARTING | HEALTHY | Health check OK | Begin accepting requests |
| HEALTHY | DEGRADED | Clock drift detected | Log warning, continue |
| HEALTHY | FAILED | Unrecoverable error | Log error, stop |
| DEGRADED | HEALTHY | Clock sync restored | Resume normal |
| DEGRADED | FAILED | Fatal error | Stop |
| HEALTHY | STOPPED | SIGTERM received | Graceful shutdown |
| FAILED | STOPPED | Process exit | Cleanup |
