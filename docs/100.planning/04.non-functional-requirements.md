## Step 1 — Availability Analysis

### 1.1 — Availability Target Definition

**Owner:** Tech Lead + DevOps
**Sprint:** Planning Sprint 1
**Timebox:** 3 hours

**Target:** 99.9% uptime (3 nines)

**Availability Calculation:**

| Period | Total Minutes | 99.9% Allowed Downtime | 99.99% Allowed Downtime |
|--------|---------------|----------------------|------------------------|
| Per day | 1,440 | 1.44 minutes | 8.64 seconds |
| Per week | 10,080 | 10.08 minutes | 60.48 seconds |
| Per month | 43,830 | 43.83 minutes | 4.38 minutes |
| Per year | 525,600 | 8.76 hours | 52.56 minutes |

**Error Budget Formula:**
```
Error Budget = (1 - Availability Target) × Total Minutes
Error Budget (monthly) = 0.001 × 43,830 = 43.83 minutes
```

### 1.2 — Component Availability Analysis

**Individual Component Availability:**

| Component | Design | Availability |
|-----------|--------|-------------|
| nginx | Single instance | 99.5% (estimated) |
| Generator 1 | Single instance | 99.5% |
| Generator 2 | Single instance | 99.5% |
| Generator 3 | Single instance | 99.5% |
| PostgreSQL | Single instance | 99.5% |
| Vite Dashboard | Stateless | 99.9% |

**System Availability (assuming independent failures):**

```
System = nginx × (Generator1 ∪ Generator2 ∪ Generator3) × PostgreSQL × Dashboard
```

**Minimum Achievable with 3 Generators (any 1 must work):**
```
Generator Subsystem = 1 - (1 - 0.995)^3 = 1 - 0.000125 = 99.9875%
```

**Total System Availability Estimate:**
```
System ≈ 0.995 × 0.999875 × 0.995 × 0.999 ≈ 98.99%
```

**Gap Analysis:**
- Target: 99.9%
- Estimated: 98.99%
- **Gap: 0.91%** — requires improvement

### 1.3 — Availability Improvement Strategies

**Improvement Options:**

| Strategy | Impact | Effort | Cost |
|----------|--------|--------|------|
| Add nginx HA (keepalived) | +0.4% | Medium | Low |
| Move PostgreSQL to HA | +0.4% | High | Medium |
| Accept current design | 0 | None | None |

**Recommendation:** Accept current design for v1 due to:
- Internal service with lower SLA expectations
- PostgreSQL persistence is optional (can degrade gracefully)
- 3-generator redundancy covers critical path

**Validation Checklist:**
- [ ] 99.9% target is aspirational, not hard requirement
- [ ] Document actual achievable availability: ~99%
- [ ] Implement health checks to remove failed generators
- [ ] Implement graceful degradation when PostgreSQL is down

## Step 2 — Performance Requirements

### 2.1 — Throughput Requirements

**Owner:** Tech Lead
**Sprint:** Planning Sprint 1
**Timebox:** 3 hours

**Business Requirement:**
> Ability to generate over 10,000 unique IDs per second

**Throughput Analysis:**

| Metric | Requirement | Design Capacity | Headroom |
|--------|-------------|-----------------|----------|
| Normal load | 10,000 RPS | 12,000 RPS (3 generators) | 1.2× |
| Peak load | 15,000 RPS | 12,000 RPS (3 generators) | 0.8× ⚠️ |
| Single generator | 10,000 RPS | 4,096,000 RPS | 409× ✓ |

**Key Insight:** Single generator can handle entire 10,000 RPS requirement. 3 instances provide redundancy, not capacity.

**Peak Load Concern:** If peak exceeds 12,000 RPS (3 × 4,096), we need:
1. Monitor actual peak usage
2. Add more generator instances (up to 32 per datacenter)
3. Update nginx configuration

**Throughput Test Scenarios:**

| Scenario | Target RPS | Duration | Pass Criteria |
|----------|-----------|----------|---------------|
| Sustained load | 10,000 | 60 min | 0 errors, all IDs unique |
| Burst load | 15,000 | 10 sec | Graceful degradation |
| Cold start | 10,000 | 5 min | No errors during warmup |

### 2.2 — Latency Requirements

**Business Requirement:**
> P99 < 50ms per ID generation request

**Latency Budget Breakdown:**

| Component | P50 | P95 | P99 | Notes |
|-----------|-----|-----|-----|-------|
| nginx routing | 0.1ms | 0.2ms | 0.5ms | Local proxy |
| Network (client → nginx) | 0.5ms | 1ms | 2ms | Local network |
| Python ID generation | 0.01ms | 0.02ms | 0.05ms | Pure computation |
| PostgreSQL write (async) | 1ms | 3ms | 5ms | Not in hot path |
| **Total (end-to-end)** | **~2ms** | **~5ms** | **~8ms** | |

**Headroom Analysis:**
```
Required: 50ms
Actual (P99): ~8ms
Headroom: 42ms (84% unused)
```

**Conclusion:** Latency requirement has ample headroom. Design is sound.

**Latency Test Scenarios:**

| Scenario | RPS | Pass Criteria |
|----------|-----|---------------|
| P50 latency | 10,000 | < 5ms |
| P95 latency | 10,000 | < 10ms |
| P99 latency | 10,000 | < 50ms |
| Timeout | - | Requests fail after 5s |

### 2.3 — Capacity Planning

**Per-Generator Capacity:**
```
Sequence bits: 12
Max per ms: 2^12 = 4,096
Max per second: 4,096 × 1,000 = 4,096,000

Throughput margin: 4,096,000 / 10,000 = 409.6×
```

```
Bits: 41
Max value: 2^41 - 1 = 2,199,023,255,551 ms
Years from epoch: ~69.7 years
End date: 2010 + 69.7 = ~2080
```

## Step 3 — Consistency & CAP Trade-off

### 3.1 — CAP Decision

**Owner:** Tech Lead
**Sprint:** Planning Sprint 1
**Timebox:** 2 hours

**Decision:** **CP (Consistency over Availability)**

**Rationale from Q4.2:**
> IDs must never collide

**Analysis:**

| Option | Pros | Cons |
|--------|------|------|
| CP (Chosen) | Zero collisions guaranteed | Service unavailable during partition |
| AP | Always available | Rare collisions possible (unacceptable) |

### 3.2 — Consistency Guarantees

**Per-Generator Guarantees:**

| Guarantee | Mechanism | Implementation |
|-----------|-----------|----------------|
| Uniqueness | Snowflake algorithm | Timestamp + Datacenter + Machine + Sequence |
| Monotonicity | Sequence number | Resets to 0 each millisecond |
| No collisions | Unique (DC, Machine) tuple | Configuration validation |

**Cross-Generator Guarantees:**

| Scenario | Outcome | Handling |
|----------|---------|----------|
| Clock drift < 1ms | Safe | Allowed, may cause minor out-of-order |
| Clock drift 1-10ms | Warning | Log warning, continue |
| Clock drift > 10ms | Error | Return 500, alert ops |
| Network partition | Degrade | 503 returned, generators continue locally |

### 3.3 — Clock Synchronization Requirements

**NTP Requirements:**

| Requirement | Value | Notes |
|-------------|-------|-------|
| Max drift | ±10ms | Triggers warning at ±1ms |
| Drift check interval | 1 second | Internal validation |
| NTP query interval | 60 seconds | System NTP daemon |
| Acceptable NTP sources | 3+ | For drift detection |

**Clock Validation Code:**
```python
class ClockValidator:
    def __init__(self):
        self._last_time_ms = 0
        self._drift_count = 0
    
    def validate(self, current_time_ms: int) -> Tuple[bool, str]:
        if current_time_ms < self._last_time_ms:
            drift = self._last_time_ms - current_time_ms
            if drift > 10:
                return False, f"CLOCK_BACKWARDS: {drift}ms"
            else:
                self._drift_count += 1
                return True, f"CLOCK_DRIFT: {drift}ms"
        
        self._last_time_ms = current_time_ms
        return True, "OK"
```

### 3.4 — Conflict Resolution

**Collision Scenarios:**

| Scenario | Probability | Mitigation |
|----------|-------------|------------|
| Same (DC, Machine, Timestamp, Sequence) | 0 (atomic) | Not possible |
| Different machines same ms + sequence | 0 (different machine bits) | Not possible |
| Timestamp overflow race | 0 (single-threaded) | Not possible |

**Conclusion:** Collisions are mathematically impossible given proper configuration.

**Output:** `docs/100.planning/16.consistency-design.md`

## Step 4 — Recoverability Requirements

### 4.1 — RPO/RTO Definition

**Owner:** Tech Lead + DevOps
**Sprint:** Planning Sprint 1
**Timebox:** 2 hours

**Recovery Point Objective (RPO):**

| Component | RPO | Rationale |
|-----------|-----|-----------|
| Generated IDs | 0 | IDs returned to client immediately; no data loss |
| Persistence | ~1 minute | Async writes may be in-flight |
| Configuration | 0 | Config is code; version controlled |

**Recovery Time Objective (RTO):**

| Component | RTO | Rationale |
|-----------|-----|-----------|
| Single generator restart | < 1 minute | Container restart within 30s + init |
| All generators down | < 5 minutes | Requires manual intervention |
| PostgreSQL failure | < 30 minutes | Database restore from backup |
| nginx failure | < 5 minutes | Manual restart required |

### 4.2 — Failure Mode Analysis

**Failure Modes:**

| Mode | Detection | Impact | Response |
|------|-----------|--------|----------|
| Generator crash | nginx health check (5s) | 33% capacity loss | Automatic LB removal |
| Generator clock issue | Internal check | ID generation fails | Return 500, alert |
| PostgreSQL down | Generator error log | Persistence fails | Continue without DB |
| nginx down | Client timeout | Total service down | Manual restart |
| Network partition | Client timeout | Service unavailable | Return 503 |

### 4.3 — Backup & Recovery

**PostgreSQL Backup Strategy:**

| Type | Frequency | Retention | RTO |
|------|-----------|-----------|-----|
| Full backup | Daily | 7 days | < 30 min |
| WAL archiving | Continuous | 7 days | < 5 min (PITR) |
| Point-in-time recovery | On-demand | - | < 30 min |

**Generator Instance Recovery:**
```bash
# Docker Compose recovery
docker-compose restart generator-1
# Expected time: 30-60 seconds
```

### 4.4 — Health Check Design

**Health Check Endpoint:** GET /health

**Implementation:**
```python
class HealthCheck:
    def __init__(self, generator):
        self.generator = generator
        self._checks = {
            'clock': self._check_clock,
            'sequence': self._check_sequence,
            'memory': self._check_memory,
        }
    
    async def get_health(self) -> dict:
        status = 'ok'
        issues = []
        
        for name, check in self._checks.items():
            result = await check()
            if not result['ok']:
                status = 'degraded'
                issues.append(result['message'])
        
        return {
            'status': status,
            'instance': self.generator.instance_id,
            'issues': issues
        }
```

**nginx Health Check Configuration:**
```nginx
upstream generators {
    least_conn;
    
    server generator-1:5001 check;
    server generator-2:5002 check;
    server generator-3:5003 check;
}

server {
    location /health {
        proxy_pass http://generators;
        health_check;
    }
}
```

### 5.3 — Authentication & Authorization

**Decision from Q4.4:**
> No authentication required for ID generation endpoint

**Rationale:**
- Internal service behind corporate network
- IDs are not sensitive data
- Authentication adds latency (conflicts with 10K RPS target)

**Future Considerations:**
- If exposed externally, add API key authentication
- If multi-tenant, add tenant isolation

| Machine ID | ID generation | Environment variable |

**Secrets Not Required:**
- No JWT tokens
- No OAuth credentials

### 5.5 — Logging Security

**Logging Rules:**
1. Never log generated IDs in full (privacy)
2. Never log PII
3. Never log secrets or tokens
4. Always include correlation ID

**Safe Log Format:**
```python
# Good
logger.info(f"Generated ID from {datacenter_id}-{machine_id}", extra={
    'correlation_id': correlation_id,
    'sequence': sequence
})

# Bad
logger.info(f"Generated ID: {full_id}")  # Don't log full ID
```

                         ['instance'])

### 6.2 — Tracing

**Correlation ID:**
```python
# Middleware to add correlation ID
@app.middleware
async def add_correlation_id(request, call_next):
    correlation_id = request.headers.get('x-correlation-id', uuid4())
    request.state.correlation_id = correlation_id
    
    response = await call_next(request)
    response.headers['x-correlation-id'] = correlation_id
    
    return response
```
