# Performance Requirements

## Overview
This document details the performance requirements including throughput, latency, and capacity planning for the Unique ID Generator service.

## Throughput Requirements

### Business Requirement

> Ability to generate over 10,000 unique IDs per second

### Throughput Analysis

| Metric | Requirement | Design Capacity | Headroom |
|--------|-------------|-----------------|----------|
| Normal load | 10,000 RPS | 12,000 RPS (3 generators) | 1.2× |
| Peak load | 15,000 RPS | 12,000 RPS (3 generators) | 0.8× ⚠️ |
| Single generator | 10,000 RPS | 4,096,000 RPS | 409× ✓ |

### Per-Generator Capacity

```
Snowflake sequence: 12 bits (0-4095)
Max IDs per millisecond: 2^12 = 4,096
Max IDs per second: 4,096 × 1,000 = 4,096,000
```

### Key Insight

**Single generator can handle the entire 10,000 RPS requirement.**

The 3 generator instances provide **redundancy**, not additional capacity.

### Peak Load Concern

| Scenario | RPS | Status |
|----------|-----|--------|
| Normal load | 10,000 | ✓ Within capacity |
| Peak load | 15,000 | ⚠️ Exceeds 3-generator capacity |

**Mitigation for Peak Load:**
1. Monitor actual peak usage in production
2. Add more generator instances (up to 32 per datacenter)
3. Update nginx configuration to include new instances

## Latency Requirements

### Business Requirement

> P99 < 50ms per ID generation request

### Latency Budget

| Component | P50 | P95 | P99 | Notes |
|-----------|-----|-----|-----|-------|
| nginx routing | 0.1ms | 0.2ms | 0.5ms | Local proxy |
| Network (client → nginx) | 0.5ms | 1ms | 2ms | Local network |
| Python ID generation | 0.01ms | 0.02ms | 0.05ms | Pure computation |
| PostgreSQL write (async) | 1ms | 3ms | 5ms | Not in hot path |
| **Total (end-to-end)** | **~2ms** | **~5ms** | **~8ms** | |

### Headroom Analysis

```
Required P99 latency: 50ms
Actual P99 latency: ~8ms
Headroom: 42ms (84% unused)
```

### Conclusion

Latency requirement has **ample headroom**. The design is sound for the 10K RPS requirement.

## Capacity Planning

### ID Generation Capacity

```
Per generator: 4,096,000 IDs/second
With 3 generators: 12,288,000 IDs/second

Required: 10,000 IDs/second
Margin: 1,228×
```

### Timestamp Overflow Timeline

```
Bits: 41
Max value: 2^41 - 1 = 2,199,023,255,551 ms
Years from epoch: ~69.7 years
End date: 2010 + 69.7 = ~2080

Action Items:
- Monitor timestamp values in production
- Plan epoch change or migration before 2080
- Add metric for timestamp remaining
```

### Database Capacity

```
For 10,000 RPS with async batch writes (batch size 100):
- DB writes per second: 10,000 / 100 = 100
- Each write holds connection for ~1ms
- Pool size 10 is sufficient

Connection pool sizing:
- Active connections = (RPS / batch_size) × connection_time
- = (10,000 / 100) × 0.001 = 0.1 connections
- With margin: pool_size = 10
```

### k6 Load Test Configuration

// k6 script for load testing
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 10000 },  // Ramp up to 10K

  ],
  thresholds: {
    http_req_duration: ['p(99)<50'],    // P99 < 50ms

    'has id': (r) => JSON.parse(r.body).id !== undefined,
  });
  sleep(0.1);  // 10 RPS per VU, need 1000 VUs for 10K RPS
}

## Bottleneck Analysis

### Potential Bottlenecks

| Component | Risk | Mitigation |
|-----------|------|-----------|
| Python GIL | Low (async I/O) | asyncio, not threading |
| Sequence overflow wait | Low (rare) | Only happens at >4096 req/ms |
| PostgreSQL writes | Low (async, batched) | Non-blocking queue |
| nginx proxy | Low | Single proxy is fast |
| Network | Low | Local network |

### Bottleneck Mitigations

1. **Python GIL:** Using asyncio (single-threaded async), not threading
2. **Sequence overflow:** Only at 4096+ req/ms, which is 409× over requirement
3. **PostgreSQL:** Async writes with queue, doesn't block ID generation
4. **nginx:** Well-optimized, handles 10K RPS easily
