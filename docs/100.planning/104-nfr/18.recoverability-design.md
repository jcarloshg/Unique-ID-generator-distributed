# Recoverability Design

## Overview
This document defines the recoverability requirements including RPO/RTO, failure modes, backup strategies, and health check design.

## RPO/RTO Definition

### Recovery Point Objective (RPO)

| Component | RPO | Rationale |
|-----------|-----|-----------|
| Generated IDs | 0 | IDs returned to client immediately; no data loss |
| Persistence | ~1 minute | Async writes may be in-flight |
| Configuration | 0 | Config is code; version controlled |

### Recovery Time Objective (RTO)

| Component | RTO | Rationale |
|-----------|-----|-----------|
| Single generator restart | < 1 minute | Container restart + init |
| All generators down | < 5 minutes | Requires manual intervention |
| PostgreSQL failure | < 30 minutes | Database restore from backup |
| nginx failure | < 5 minutes | Manual restart required |

## Failure Mode Analysis

### Failure Modes

| Mode | Detection | Impact | Response |
|------|-----------|--------|----------|
| Generator crash | nginx health check (5s) | 33% capacity loss | Automatic LB removal |
| Generator clock issue | Internal check | ID generation fails | Return 500, alert |
| PostgreSQL down | Generator error log | Persistence fails | Continue without DB |
| nginx down | Client timeout | Total service down | Manual restart |
| Network partition | Client timeout | Service unavailable | Return 503 |

### Failure Response Matrix

| Failure | nginx Behavior | Client Impact | Recovery |
|---------|---------------|---------------|----------|
| 1 generator down | Route to others | None (transparent) | Auto via health check |
| 2 generators down | Route to 1 | Higher latency | Manual restore |
| All generators down | 503 error | Service unavailable | Manual restart |
| PostgreSQL down | None (async) | None (IDs still generated) | Auto when restored |
| nginx down | N/A | Total outage | Manual restart |

## Backup & Recovery

### PostgreSQL Backup Strategy

| Type | Frequency | Retention | RTO |
|------|-----------|-----------|-----|
| Full backup | Daily | 7 days | < 30 min |
| WAL archiving | Continuous | 7 days | < 5 min (PITR) |
| Point-in-time recovery | On-demand | - | < 30 min |

### Backup Configuration

```sql
-- Enable WAL archiving
ALTER SYSTEM SET wal_level = replica;
ALTER SYSTEM SET archive_mode = on;
ALTER SYSTEM SET archive_command = 'test ! -f /mnt/wal/%f && cp %p /mnt/wal/%f';

-- Backup retention
SELECT pg_create_restore_point('before_upgrade');

-- Point-in-time recovery
-- psql -c "SELECT pg_restore('#BACKUP_DATE#')"
```

### Generator Instance Recovery

```bash
# Docker Compose recovery
docker-compose restart generator-1
# Expected time: 30-60 seconds

# Kubernetes recovery (future)
kubectl rollout restart deployment/generator
# Expected time: 30-60 seconds
```

## Health Check Design

### Health Check Endpoint

**GET /health**

```json
{
  "status": "ok",
  "instance": "dc-01-machine-03",
  "uptime_seconds": 86400,
  "ids_generated": 1234567890
}
```

### Health Check Implementation

```python
class HealthCheck:
    def __init__(self, generator):
        self.generator = generator
        self._checks = {
            'clock': self._check_clock,
            'sequence': self._check_sequence,
            'memory': self._check_memory,
        }

    async def get_health(self) -> dict:
        status = 'ok'
        issues = []

        for name, check in self._checks.items():
            result = await check()
            if not result['ok']:
                status = 'degraded' if status == 'ok' else status
                issues.append(result['message'])

        return {
            'status': status,
            'instance': self.generator.instance_id,
            'uptime_seconds': self.generator.uptime_seconds,
            'ids_generated': self.generator.ids_generated,
            'issues': issues
        }

    async def _check_clock(self) -> dict:
        drift = self.generator.get_clock_drift()
        if drift > 10:
            return {'ok': False, 'message': f'Clock drift {drift}ms'}
        elif drift > 1:
            return {'ok': True, 'message': f'Clock warning {drift}ms'}
        return {'ok': True, 'message': 'Clock OK'}
```

### nginx Health Check Configuration

```nginx
upstream generators {
    least_conn;

    server generator-1:5001 check inter=5s rise=2 fall=3;
    server generator-2:5002 check inter=5s rise=2 fall=3;
    server generator-3:5003 check inter=5s rise=2 fall=3;
}

server {
    location / {
        proxy_pass http://generators;
        proxy_connect_timeout 5s;
        proxy_read_timeout 10s;
    }

    location /health {
        proxy_pass http://generators;
        health_check type=http uri=/health;
    }
}
```

## Graceful Degradation

### PostgreSQL Unavailable

| State | Behavior |
|-------|----------|
| Available | Async writes enabled |
| Unavailable | Continue generating IDs, skip writes, log warning |
| Recovered | Resume writes automatically |

### Generator Unavailable

| State | Behavior |
|-------|----------|
| Healthy | Accepts requests |
| Degraded | Accepts requests with warnings |
| Down | nginx removes from pool |

## Disaster Recovery

### DR Scenarios

| Scenario | Impact | Recovery Steps | RTO |
|----------|--------|----------------|-----|
| Single generator down | 33% capacity | Restart container | < 1 min |
| All generators down | Total outage | Restart all generators | < 5 min |
| PostgreSQL data loss | Audit gap | Restore from backup | < 30 min |
| nginx down | Total outage | Restart nginx | < 5 min |
| Host failure | Total outage | Redeploy all | < 1 hour |

### DR Runbook

1. **Identify failure** → Check monitoring/alerting
2. **Assess impact** → Determine affected components
3. **Execute recovery** → Follow component-specific runbook
4. **Verify recovery** → Confirm service restored
5. **Post-incident review** → Document lessons learned
