## 1. Business Context

### Q1.1 — Business Model
This is an internal infrastructure project that provides a distributed unique ID generation service. The service generates globally unique, time-ordered, 64-bit numerical IDs for use by other services in the organization. The paying user is the internal development team or organization that consumes the ID generation API.

### Q1.2 — Core Workflow
1. Client service requests a new unique ID via HTTP API
2. Load balancer (nginx) routes request to one of 3 generator instances
3. Generator creates ID using Snowflake-like algorithm (timestamp + datacenter + machine + sequence)
4. ID is returned to client
5. (Optional) ID may be logged to PostgreSQL for auditing/verification

### Q1.3 — Domain Glossary
- **ID:** A 64-bit unsigned integer that is globally unique and time-ordered
- **Timestamp:** Milliseconds since epoch (Twitter Snowflake epoch: 1288834974657)
- **Datacenter ID:** 5-bit identifier for the datacenter (0-31)
- **Machine ID:** 5-bit identifier for the machine within a datacenter (0-31)
- **Sequence Number:** 12-bit counter that resets every millisecond (0-4095)
- **Generator Service:** Python service that produces IDs
- **Load Balancer:** Nginx instance that distributes requests

### Q1.4 — Domain Events
- `IdGenerated` — An ID was successfully generated and returned
- `IdPersisted` — An ID was logged to PostgreSQL (if enabled)
- `GeneratorStartup` — A generator instance started
- `GeneratorShutdown` — A generator instance stopped

### Q1.5 — Bounded Context Candidates
- **ID Generation Context** — Core domain logic for generating unique IDs (Python service)
- **Persistence Context** — PostgreSQL storage for ID auditing/logging
- **Load Balancing Context** — Nginx routing layer
- **Client Interface Context** — Vite web app for monitoring/admin

### Q1.6 — Business Rules
- An ID must never collide with another ID across all generators
- IDs must be monotonically increasing (time-ordered) when generated on the same machine
- The system must sustain 10,000+ ID generations per second
- Sequence number resets to 0 every millisecond per machine

## 2. Technical Requirements

### Q2.1 — ID Structure (64 bits total)
```
| Sign Bit (1) | Timestamp (41) | Datacenter ID (5) | Machine ID (5) | Sequence (12) |
|     0        |   ms since epoch |      0-31        |     0-31       |    0-4095      |
```

### Q2.2 — Quantified NFRs
- **Throughput:** ≥ 10,000 unique IDs per second
- **Latency:** P99 < 50ms per ID generation request
- **Availability:** 99.9% uptime (3 nines)
- **ID Size:** Must fit in 64-bit unsigned integer
- **Uniqueness:** Zero collisions across all generators
- **Sortability:** Time-ordered (by timestamp component)

### Q2.3 — Technical Stack
| Component | Technology | Count |
|-----------|------------|-------|
| Load Balancer | nginx | 1 |
| Generator Service | Python | 3 |
| Database | PostgreSQL | 1 |
| Web Dashboard | Vite | 1 |
| Container Platform | Docker | - |

### Q2.4 — Infrastructure Constraints
- 3 generator instances for redundancy
- 1 PostgreSQL instance for persistence
- nginx as single entry point
- Docker for containerization

## 3. Functional Requirements

### Q3.1 — Core Features
1. Generate unique 64-bit IDs via HTTP GET endpoint
2. Return IDs as numerical values (JSON)
3. Support concurrent requests without collisions
4. Time-based ordering within a single generator
5. Persist generated IDs to PostgreSQL (optional/auditing)
6. Web dashboard to monitor generator health

### Q3.2 — API Contract
```
GET /generate → { "id": <64-bit-integer> }
GET /health → { "status": "ok", "instance": "<datacenter>-<machine>" }
```

### Q3.3 — Error Handling
- 503 Service Unavailable if all generators are down
- 500 Internal Server Error on generator failure
- Timeout after 5 seconds

## 4. Non-Functional Requirements

### Q4.1 — Availability
- Target: 99.9% (3 nines)
- Monthly error budget: ~43.8 minutes
- Graceful degradation: if one generator fails, others continue

### Q4.2 — CAP Trade-off
- **Consistency** (CP) over Availability — IDs must never collide
- Network partitions will result in service degradation, not silent collisions

### Q4.3 — RPO/RTO
- RPO: 0 (no data loss for generated IDs; they are returned to client)
- RTO: < 1 minute for generator instance restart

### Q4.4 — Security
- Internal service only (no external exposure planned)
- No PII involved
- No authentication required for ID generation endpoint

## Quick-Reference Summary

### Project Snapshot
A distributed unique ID generation service inspired by Twitter Snowflake. Generates globally unique, time-ordered, 64-bit numerical IDs at 10,000+ per second across 3 generator instances with nginx load balancing and optional PostgreSQL persistence. Internal infrastructure service consumed by other organization services.

### Key Targets
- **Throughput:** ≥ 10,000 IDs/second sustained
- **Latency:** P99 < 50ms
- **Availability:** 99.9% (3 nines)
- **ID Format:** 64-bit unsigned integer
- **CAP Choice:** CP (Consistency over Availability)
- **RTO:** < 1 minute for instance restart

### Bounded Contexts
- **ID Generation** — Core Snowflake-like algorithm, Python service
- **Persistence** — PostgreSQL for ID auditing
- **Load Balancing** — nginx routing layer
- **Monitoring** — Vite web dashboard

### Critical Constraints
- Zero ID collision tolerance (strict consistency)
- 64-bit constraint (no overflow)
- 3-instance redundancy requirement
- Single PostgreSQL instance (not distributed)
